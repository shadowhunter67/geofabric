# ADR-009 — Runtime capability probing (static capabilities ≠ what the runtime does)

Status: Proposed (2026-10-14)

**Decision.** The planner keeps three layers apart: (1) *static capabilities* — what an engine is designed for (`EngineDescriptor::capabilities`); (2) a *runtime probe* — what this runtime instance demonstrably does right now; (3) *observed health* — how real queries have been going (ADR-010). The browser engine probes itself (`web/src/engine/probe.ts`) after the page loads and reports a `ProbeReport` to the gateway (`POST /api/probe`). The probe runs the engine's **real execution path** — the PlanGraph→SQL compiler and the streaming result reader — on two tiny fixture files (`web/public/probe/`, one per GeoParquet writer class) and one tiny plan per operation kind, so a defect anywhere on that path shows up in the probe instead of in a user's query.

Checks: `worker`, `init` (instantiate DuckDB-Wasm, `SELECT version()`), `arrow`, `extension_load` (information), `parquet`, `http_range` (the large-file path), `geometry_wkb`, `covering` (bbox filtering through the covering columns), `read_class:plain_wkb`, `read_class:duckdb_typed`, `op:<kind>` per operator. Required checks failing ⇒ the browser candidate is infeasible with the reason in the plan. The report also carries engine version, runtime (DuckDB) version, memory class (`navigator.deviceMemory`), JS heap limit, supported operations, timing.

**Cache and invalidation.** One report per engine, per page session. A page reload is a new session (the client probes again at startup); the gateway replaces the old report. TTL: the client re-probes after 25 min, the planner treats a report older than 30 min as *stale* (still usable, lower confidence). A different engine version clears the engine's health history and known incompatibilities. A crash or out-of-memory failure removes the probe and the client re-probes the fresh instance in the background. An unprobed browser is never selected on a cost advantage alone (rule R5b); an explicit engine hint still reaches it.

**What the probe found on its first day (2026-10-14).** It is not decoration; it corrected three beliefs the previous phase had recorded as facts:

1. *"DuckDB-Wasm cannot read Overture's native Parquet GEOMETRY."* False. It reads the file; **streaming** a `GEOMETRY('OGC:CRS84')` column out of DuckDB-Wasm fails with `TransactionContext::ActiveTransaction called without active transaction` (reproduced: `conn.send` fails, `conn.query` works; a cast to `BLOB` is unimplemented, `ST_AsWKB` and a cast to plain `GEOMETRY` work). The defect was in the TypeScript lowering (the Rust lowering already converts at the scan). Fixed in `sqlgen.ts` (`ST_AsWKB` in the source CTE); the Overture subset now runs in the browser with identical digests (count_by, features).
2. *"DuckDB-Wasm does not prune row groups through struct statistics; it reads every covering chunk."* Not what was happening: with the default configuration **it downloaded the whole file in a single request** (`GET`, no `Range`, status 200 — 98 MB for a 100 MB file, on every query). All earlier browser timings, the crossover fit and the 245 MB "crash threshold" (which was a planner *estimate* of covering + kept bytes, not a measurement) were measurements of whole-file downloads. Fix: `db.open({filesystem: {reliableHeadRequests: true, allowFullHTTPReads: false}})` makes it use real range requests.
3. *Range requests are not free.* DuckDB-Wasm issues them synchronously, one after another: ≈ 9.6 requests per touched row group for an aggregate, 14.5 ms each on loopback. A 10 MB file is faster to download whole (1 request) than to read by ranges (28+ requests); a 100 MB file the other way round on a slow link. The planner therefore chooses the **access strategy per source** (`assessment.browser_access`: `full` up to 32 MB, `range` above) and the client follows it. One more trap found on the way: DuckDB caches Parquet metadata by file name, so reusing `gf_src_0.parquet` for a different file gave "No magic bytes found at end of file"; every execution now registers uniquely named files.

**Evidence.** 20 planner unit tests, 12 hardening tests on real footers (probe failure, class unreadable, stale probe, unhealthy engine, known incompatibility, network profiles, cold start, risk by memory class), 12 gateway tests (probe validation, reports, state, simulated network), 7 browser tests (real Chrome: probe passes, pre-rejection, UI fields, bounded fallback), TS unit tests, and the measurement campaign in `REPORT-GEOFABRIC-PLANNER-HARDENING.md` (all browser runs digest-equal to the server).

**Limits.** The probe tests *this* tab's engine on tiny files; it cannot prove a 1 GB file fits in memory — the memory model (ADR-010, risk score) is an estimate whose single anchor is "the old whole-file downloads of 1 GB+ crashed the tab; ≤ 100 MB did not". Memory class scaling below 8 GB devices is an assumption. A probe is a snapshot: tab memory pressure after the probe is not seen until a run fails (health, ADR-010). Status stays Proposed until a second browser/device has been probed.
