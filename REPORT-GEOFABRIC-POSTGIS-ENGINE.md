# REPORT — GeoFabric PostGIS engine (2026-10-20)

Written for: the Principal Architect, who asked whether a genuinely different engine family can sit under the existing abstraction.

## Executive Summary

**The abstraction held; the engine has never run against a real PostgreSQL.** When the phase asked to install PostGIS, the machine had no Docker, Podman, WSL or PostgreSQL. A privilege-free route existed (portable zips, 440 MB, pinned and checksummed) and I asked before downloading, as the project rules require; the answer was "do not download, stop at design". So this phase delivers the design and everything that can be verified **without a database**, and it says plainly what that does not prove.

## Configuration

`GEOFABRIC_POSTGIS_ENABLED` / `_URL` / `_SOURCES` / `_POOL`. Disabled or absent = no engine, no probe, no startup error (test `geofabric_runs_normally_without_postgis`). A malformed configuration disables PostGIS and is logged; the gateway still starts. Configured but built without the driver: the engine exists, is unhealthy and says why ("no PostgreSQL driver in this build") — never silently absent (test `a_configured_but_driverless_build_is_visible_and_explained_not_silent`).

## Security / Credentials

The URL (with password) is held in `PostGisConfig`, whose `Debug` redacts it (tested); it appears in no log, state endpoint or error. Local development credentials are generated by the setup script into the gitignored `tools/.cache/postgres/credentials.json`; nothing secret is committed. Topology is Browser → Gateway → PostGIS; the database binds 127.0.0.1 only. Roles: `gf_admin` (owner; setup/import) and `gf_reader` (SELECT only; the runtime account) — designed, not exercised. No TLS in the driver (local development only, stated). Identifiers come only from the validated catalog; all values are bind parameters (see SQL Lowering). `execute` authorizes every source through the access guard **before** the catalog or the database is touched (test: a denying guard → `AccessDenied`, zero connector calls); the probe reads system catalogs only (`version()`, `postgis_full_version()`, `pg_proc`), never a user relation.

It has never been run.

## Data Parity

**Not done** (no data in any database). The loader's parity check (row count, SRID values) is the intended gate; nothing was compared.

## Spatial Indexes

**Not done.** The loader creates `GIST` on the geometry column and `ANALYZE`s; the lowering uses `geometry && ST_MakeEnvelope(...)` (index-assisted) for bbox filters. No `EXPLAIN` was run, so **no index-use evidence exists**. One known limit: the metric predicate runs on `ST_Transform` of the stored geometry, so it cannot use the stored column's index (a functional index or a safe prefilter would be needed) — a performance risk to measure, recorded in ADR-013.

## EngineDescriptor

`PostGisEngine` implements `EngineDescriptor`: id `postgis`, kind Server, locality "PostgreSQL/PostGIS database server", capabilities (below), `estimate` (catalog row estimate, labelled `SourceEstimated`; bytes `Unknown`), `explain` (residency, dropped columns, the SQL with its bind-parameter count and no values). Two defaulted additions to the trait, so DuckDB and the browser descriptor are untouched: `source_residency(plan, ctx)` and `calibration()`.

## ExecutionEngine

`execute` follows one order: validate → authorize every source → residency + lowering (pure) → cancel check → `PgConnector::query` with the context's timeout → error mapping → row cap → GeoArrow tagging (now shared in `geo_executor::tag_geometry`) → metrics. Metric provenance: `elapsed_ms`, `rows_returned` EngineObserved; `rows_scanned_upper_bound` SourceEstimated; `bytes_read` and `peak_memory_bytes` Unknown (nothing fabricated). Tested with a mock connector (8 tests).

## Capability Matrix

Supported: Source, Filter, BboxFilter, Intersects, Transform, SpatialSemiJoin, Aggregate, Project, Limit, Sort. Refused with a reason: Buffer, SpatialJoin (deferred), render sampling `HashBucket` (no portable byte-exact equivalent of DuckDB's `md5_number_lower`). A test asserts the declared matrix equals what the lowering implements, and a runtime test shows a plan with a spatial join is excluded by the planner *without the server being asked*.

## SQL Lowering

PlanGraph → one CTE chain + `SELECT` with `$n::type` placeholders. Verified (9 tests): the statement text contains none of the values (`primary`, `3.5`, coordinates, WKT, hostile strings), parameters are in order, the final select converts geometry with `ST_AsBinary(g, 'NDR')`, unknown or hostile identifiers are refused, comparisons that would need a type coercion are refused, and **every generated statement parses with `sqlparser`'s PostgreSQL dialect** (syntax only). PostgreSQL defaults that differ from DuckDB are neutralized explicitly: `NULLS LAST` both directions, `COLLATE "C"` on text sort keys, little-endian WKB, explicit casts. Debt: this is a third independent compiler of the IR (DuckDB/Rust, browser/TypeScript, PostGIS/Rust); the shared "SQL intent + dialect printers" design of RFC-004 is not realized and not made worse in kind, only in count.

## CRS / Metric Semantics

`EPSG:n → n`; `OGC:CRS84 → 4326` with the axis order stated in code and ADR (stored x = lon, y = lat); CRS84 and EPSG:4326 stay different CRSs at the semantic layer (a relation of one does not satisfy a plan of the other; tested); undefined/unknown CRS is an error. `Transform` is `ST_Transform(ST_SetSRID(g, from), to)` into a new column. No `geography`. A metric predicate requires a local metric CRS and a linear unit (degrees refused; tested). **Equivalence with the DuckDB result on real data is not verified.**

## SpatialSemiJoin

Lowered as `WHERE EXISTS (SELECT 1 FROM right r WHERE ST_DWithin(l.g, r.g, $d))` — each left row at most once, no join, no DISTINCT, no pair table (tested on the Demo B plan shape). Correct-by-construction is not the same as correct: no run against data.

## Cancellation / Timeout

Verified: a cancelled context never reaches the server; driver `Timeout`/`Cancelled` map to `EngineError::Timeout{limit}` / `Cancelled`; the row cap is enforced even if a server returns more. **Not verified:** the real thing — `SET statement_timeout` and the server-side cancel request issued by the watcher thread in `live.rs`; the acceptance tests for both (`pg_sleep` with a 300 ms deadline, cancel after 200 ms, bounded pool) are written and skip.

## Health / Runtime Probe

Probe evaluation is a pure function (versions, required functions, extension present) with every missing piece named (3 tests); an unreachable server is its own state. Health: the runtime used to blame every execution failure on `"duckdb"` (hard-coded in the gateway); it now records the failure under the engine that ran, classified by the planner's own classifier. Verified with the real planner state: three PostgreSQL connection failures make `postgis` Unhealthy, DuckDB is not blamed, and the next plan routes to DuckDB without asking the database again.

## Source Locality

Three localities are now explicit: file-backed (DuckDB), database-resident (PostGIS catalog), browser-accessible (Wasm). Minimal `LogicalDataset → PhysicalSource` mapping via the catalog keyed by the logical uri; `source_residency` makes a non-resident source, a CRS mismatch or a column the relation does not store a **planning-time** rejection with a reason (tested through the runtime). Known limitation: planning still reads the Parquet footer of the logical file, so a dataset that exists only in PostGIS is not plannable yet (P1: source-metadata provider).

## Planner Integration

PostGIS competes in the same planner as DuckDB and DuckDB-Wasm; candidates carry its feasibility, reasons, calibration state and confidence; nothing in the planner mentions it by name or by dataset. Verified: it appears as a candidate with "stand-in cost", an explicit `preferred_engine: postgis` runs through the ordinary `Runtime::dispatch`; a non-resident source or an undeclared operation excludes it before any query; unconfigured, it is absent and nothing else changes.

## Cost Model v0

**Deliberately none.** There are no measurements, and inventing numbers would be fabricated evidence. The descriptor reports `Unmeasured`; the planner prices it with the DuckDB server model as a **labelled stand-in**, halves its confidence factor, and policy **R5d** never lets an unmeasured engine win on predicted cost while a measured engine can run the plan. Verified in the hardest case: PostGIS registered first so that equal stand-in costs tie to it — the planner still chooses DuckDB and records "R5d uncalibrated engine…". An explicit hint, or being the only feasible engine, selects it.

## Cross-Engine Correctness

**Not done.** The same PlanGraph has not been executed on DuckDB and PostGIS. What exists instead: lowering tests that pin the semantic choices the two dialects must agree on, and a runbook (`docs/postgis.md`) for the digest comparison through `POST /api/query` with `"engine"` set to each. Geometry comparison on real data will need topological/normalized equality where byte equality is not stable (the comparator does not exist yet).

## UI / Observability

Explorer mode never mentions PostGIS (tested: the page text does not contain it). Developer mode shows `PostGIS: not configured` (tested), or, when configured, the PostgreSQL/PostGIS versions or "configured, not usable" with the first failed check and the number of resident sources; PostGIS appears in the engine health list and in the alternatives with its reasons whenever it is registered. Execution metrics carry engine, duration, rows, fallback, confidence and policy as for any engine; PostgreSQL query-plan summaries and index status are **not** shown (they need a server).

## Failure / Fallback

Bounded and unchanged: the browser falls back to the selected server engine at most once; a failing server engine fails clearly (no retry storm, no browser→PostGIS→DuckDB chain). An unhealthy PostGIS is removed from planning (tested); a PostGIS failure does not silently re-run on DuckDB, because the same logical data is not guaranteed to be identical — it needs an explicit policy decision (open item).

## Architecture Fitness

`tools/arch_check.py` gained family isolation (first match wins): `geo-engine-postgis` may not depend on `geo-engine-duckdb`, `geo-engine-browser`, `geo-source-*`, `duckdb`, `libduckdb-sys`, planner, runtime or UI; `geo-engine-duckdb` and `geo-engine-browser` may not depend on `geo-engine-postgis`, `postgres`, `tokio-postgres`, `sqlx`; `geo-planner` may not depend on any `geo-engine-*`; `geo-gateway` may not depend on a PostgreSQL driver directly. Result: no violations; the self-test (`--extra-forbid`) proves the checker catches a violation. "Web importing the adapter" is already impossible (the adapter is Rust; `pg`/`postgres` are forbidden npm packages).

## Remaining Risks

1. **Everything requiring a server is unverified**: SQL acceptance and semantics on real PostgreSQL, data parity, geometry equality, index use, performance, the live driver (pool, timeout, cancel), the setup and import scripts. A mock proves the engine's logic, not PostgreSQL's behaviour.
2. The metric semi-join transforms on the fly and cannot use the stored geometry's GiST index: potentially slow on large tables.
3. Three independent lowerings of one IR (semantic drift risk); the canonical lowering is still owed.
4. PostGIS-only datasets are not plannable (planner reads Parquet footers).
5. PostGIS has no measured cost; R5d makes it opt-in by hint until it has one. Fallback from a failed PostGIS to DuckDB needs an explicit data-equivalence rule.
6. EDB archive checksum is trust-on-first-use; Windows-only portable route (Docker/Linux paths not written).
7. Hash-bucket sampling, Buffer and SpatialJoin are not supported.

Only then the shared-lowering (RFC-004) phase.
