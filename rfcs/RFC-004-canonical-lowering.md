# RFC-004 — Canonical lowering for the browser dialect

Status: Proposed (2026-10-14), **direction chosen 2026-10-15; step 1 implemented, step 2 designed.** No IR or wire-format change under any step.

## Problem (architecture debt, P1)

The logical plan (PlanGraph, IR 0.2) was lowered to SQL **twice, by hand, in two languages**:

| | Rust | TypeScript |
|---|---|---|
| file | `geo-engine-duckdb/src/sql.rs` (all 10 operators, server dialect) | `web/src/engine/sqlgen.ts` (7 operators, browser dialect) |
| runs in | the gateway (DuckDB + spatial extension) | the browser (DuckDB-Wasm, no spatial extension) |

They must agree on identifier quoting, literal escaping, NULL/comparison semantics, `bbox_filter` through the covering columns, the result column order and the geometry encoding. The only guard was the cross-engine digest test: a good oracle but a *late* one, only for the plans somebody wrote a test for. The duplication already bit once: typed `GEOMETRY(crs)` columns cannot be streamed out of DuckDB-Wasm; the Rust lowering converted at the scan, the TypeScript one did not, and for a week the planner "knew" that DuckDB-Wasm could not read the Overture file (ADR-009).

Note the two lowerings are *different dialects* (server: spatial functions, `ST_AsWKB` on the final projection; browser: covering-column bbox, `ST_AsWKB` at the scan). Only the **browser dialect** exists twice in spirit (it must be identical in what the planner promises and what the client runs); the server dialect has one implementation.

## Options considered

**A. One compiler, two hosts (compile the Rust lowering to WebAssembly).** One implementation. Cost: a second wasm module in the page, the lowering must be split from the source crate (it reads file metadata today), the browser build depends on the Rust→wasm toolchain.

**B. Serialized lowering instructions generated by the planner side.** The Rust side lowers the PlanGraph for the browser dialect and the client only *executes* the SQL it is given. The lowering exists once, in Rust, next to the planner that chose the browser. Cost: a few KB of SQL in the plan response.

**C. Substrait between planner and engines.** Standard, but it covers relational algebra, not GeoFabric's spatial/CRS/unit semantics, and DuckDB-Wasm does not ship the extension. Premature.

**D. Declarative operator schema + code generation for both languages.** Removes hand-written duplication without shipping SQL, but adds a generator and a schema language for ~250 lines of logic.

**E. Two compilers + golden conformance fixtures.** Tests only; drift is *detected*, not made impossible.

## Decision

**B, reached through E.** Step 1 makes the Rust browser-dialect lowering the *reference* and proves parity with the existing TypeScript twin; step 2 makes the TypeScript twin unnecessary.

Why B and not A: the browser does not need to understand plans at all; it needs SQL, file names and the covering paths — all of which the gateway already knows. A would put a Rust toolchain into the web build to run 170 lines. Why not D: the generator costs more than the duplication it removes. Trust: the SQL is produced by the gateway from a validated IR and authorized sources and runs in the client's own wasm sandbox against files the client fetched; the client already executes JavaScript from the same gateway, so no new trust boundary opens. The gateway still **accepts** no SQL from clients.

## Migration plan

1. **Done (2026-10-15).** `geo_engine_browser::lower::lower_browser` is the reference of the browser dialect. Eight golden fixtures (`crates/geo-engine-browser/tests/fixtures/lowering/*.json`: plan + sources + expected SQL or expected error) are generated from it; `cargo test` checks them against the reference and `web/test/lowering.test.ts` requires `sqlgen.ts` to produce **byte-identical SQL** for every fixture. Both pass today, so the twins agree on: scan conversion, bbox via covering, string escaping, boolean expression nesting, numeric aggregates, group-by + sort + limit, error classes. A change to either side now fails a test on the other.
2. **Next.** `client_response` returns `browser_sql` and the ordered source list produced by `lower_browser` (the gateway already holds the plan and the bindings). The client executes it when present and keeps `sqlgen.ts` only as a fallback behind a flag; a Chrome test runs both on the same plans and requires equal digests. The runtime probe asks the gateway to lower its mini-plans instead of compiling them in the page.
3. **Then.** After one release with zero divergence, delete `sqlgen.ts` and its fixtures twin test; the parity test becomes "the SQL the gateway ships equals the golden file".
4. **Optional.** Extend the same Rust crate with the server dialect behind a `dialect` parameter so that both dialects share quoting/expression code (today `sql.rs` has its own copy of `q_ident`, `lit`, `expr`).

## Risks

- *Divergence between the reference and what DuckDB-Wasm accepts*: the fixtures check text, not execution. Mitigation: the runtime probe executes real lowered plans in every client session (it found the streaming defect), and the digest tests execute them.
- *Float formatting*: Rust `Display` and JS `Number#toString` agree for ordinary magnitudes; they differ for exponents (`1e21`). The fixtures avoid them and `lower_browser` rejects non-finite numbers; huge/small literals should be rejected explicitly in step 2.
- *Larger responses*: the SQL grows with the plan (a few KB). The IR is already shipped to the client for the same plan.
- *Server dialect*: unchanged by this RFC; step 4 is optional and independent.

## Not decided here

The IR serialisation (0.2) does not change. The planner does not learn SQL (the planner returns the plan; the lowering is invoked by the gateway when the browser is selected). ADR-008 stays Proposed.
